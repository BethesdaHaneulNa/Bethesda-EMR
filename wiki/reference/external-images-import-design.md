# 설계안 — 다른 병원의 영상(CD · USB) 들여오기

> 2026-10-02 · PACS 세션 → 총괄 → 실장님. **아직 짓지 않았습니다** — 설계와, 설계의 근거로 삼으려고 임시 영상 서버에서 해 본 작은 실험뿐입니다. 17절의 결정이 나면 16절의 차례대로 짓습니다(프로그램 쪽은 반출 프로그램을 `.exe`로 옮긴 뒤 — 「Bethesda CD」 안에 처음부터 C#으로).
> 실장님(2026-10-02): 「다른 병원에서 가져온 cd나 usb 쨋든 다이콤 파일 가져오면 우리쪽으로 업로드도 가능해?」 → 총괄이 얼개를 말씀드림 → 「ㅇㅇ 너 말대로 진행해」.
> **「확인함」** 은 원문 · 코드를 읽었거나 이 PC의 임시 서버 · 격리 스택에서 실제로 해 본 것, **「추측」** 은 그렇지 않은 것입니다.

## 0. 실장님께 — 한 장으로

**무엇이 되나**: 환자가 다른 병원에서 받은 CD나 USB를 가져오면, 그 안의 영상을 **우리 영상 서버에 넣고 그 환자의 차트에 붙입니다.** 그 뒤로는 우리가 찍은 영상과 똑같이 진료 화면의 「영상/판독」 목록에서 열리고(「외부」 표시가 붙음), 우리 영상과 나란히 비교할 수 있습니다.

**어떻게 하나**(직원이 보는 차례)
1. 「Bethesda CD」 프로그램(지금의 CD 반출 프로그램)에 **「들여오기」** 가 생깁니다. 본인 계정으로 로그인하고 차트번호로 환자를 고릅니다.
2. CD(또는 USB의 폴더)를 고르면 그 안의 검사 목록이 나옵니다 — 날짜 · 종류 · 장수 · 크기 · **디스크에 적힌 환자 이름과 병원**.
3. 가져올 검사를 고르면 **「디스크의 이름 ○○○(생일 …) / 우리 차트 △△△(생일 …) — 같은 환자입니까?」** 를 묻습니다. 생일이나 성별이 다르면 빨갛게 보이고, 그래도 맞다고 표시해야 넘어갑니다.
4. 올라가는 동안 진행 표시. 끝나면 진료 화면의 목록에 「외부」 표시와 함께 나옵니다.

**영상은 어떻게 바뀌나**: **그림은 한 점도 바꾸지 않습니다**(압축도 그대로 — 실험으로 확인). 영상 안에 적힌 **환자 번호와 이름만 우리 차트의 것으로** 바꿉니다(그래야 우리 화면 · CD 반출 · 환자 번호 대조가 그대로 돕니다). 원래 병원 이름 · 검사 날짜 · 검사 이름은 남기고, **원래의 환자 번호와 이름도 영상 안의 따로 마련된 자리에 남깁니다.**

**안전장치**: 환자 확인 창(위 3) · 같은 검사를 두 번 넣지 않음 · 올리다 끊기면 반쯤 올라간 것을 스스로 지움 · 누가 언제 어느 디스크의 무엇을 누구 차트에 넣었는지 변경 기록 · 디스크에 든 다른 회사의 프로그램은 실행하지도 복사하지도 않음(영상 파일만 읽음) · 큰 검사는 크기를 보여 주고 고르게 하고, 서버에 자리가 모자라면 받지 않음.

**실장님이 정하실 것**(17절에 추천과 함께): ① 의사가 먼저 「외부 영상」 오더를 내야 들여올 수 있게 할지, 접수에서 바로 들여오게 할지 ② 생일이 다를 때 막을지 경고만 할지 ③ 외부 영상에 우리 의사가 판독을 쓸 수 있게 할지 ④ 들여온 영상을 우리 CD 반출에 다시 넣을 수 있게 할지 ⑤ 등록비 ⑥ 한 번에 들여올 수 있는 크기의 한도 ⑦ 누가 할 수 있는지.

## 1. 한눈에

| | |
|---|---|
| 어디서 | 「Bethesda CD」 프로그램의 **「Importer」** 갈래(「Copier vers un CD」 옆). 프로그램은 지금처럼 **EMR만** 부름 — 영상 서버의 비밀번호는 프로그램에 없음 |
| 무엇을 읽나 | CD · USB · 폴더의 **DICOM 파일만**(`DICM` 표시가 있는 파일). `DICOMDIR`이 있으면 목록을 빨리 만드는 데 쓰고, 없으면 파일을 훑음. 뷰어 · DLL · `AUTORUN.INF`는 읽지도 실행하지도 복사하지도 않음 |
| 영상 서버 | Orthanc의 **공식 REST만**(`POST /instances` · `POST /instances/{id}/modify` · `DELETE` · `POST /tools/find`). Orthanc를 고치지 않음 |
| 바꾸는 것 | 환자 번호 · 이름 · 생일 · 성별(우리 차트 것), 검사 번호(우리 규칙의 새 번호), accession(우리 규칙). **그림 · 압축 · 시리즈/영상 번호 · 원래 병원 · 날짜 · 설명은 그대로**(3절) |
| EMR에서 | 「외부 영상」 오더(0 Ar) 하나 = 디스크의 검사 하나. 장비 워크리스트에는 **안 나감**. 목록 · 영상 창 · 비교 · 인쇄에 우리 영상처럼 나오고 「외부」 표시 |
| 기록 | 변경 기록 `pacs.images.import` 한 줄 + 들여오기 표 `pacs_import`(원래 이름 · 번호 · 병원 · 날짜, 누가, 언제, 몇 장) |
| 새로 필요한 것 | EMR: 길 넷(15절) · 마이그레이션 하나(총괄이 번호 — 050) · nginx 설정 한 군데(큰 파일 올리기 — 지금 한도 1MB) · 진료 세션과 맞출 것 하나(5절). PACS: 브리지가 저장 공간을 보고(10절). 프로그램: 「들여오기」 화면 |

- 생일 · 성별은 양쪽에 다 있고 **다르면 그 줄이 빨강**, 체크 글이 「Les dates de naissance sont différentes. Je confirme malgré tout…」로 바뀝니다(17절 나).

## 3. 영상 안에서 바꾸는 것 · 남기는 것

| 태그 | 들여온 뒤 | 왜 |
|---|---|---|
| PatientID (0010,0020) | **우리 차트번호** | 우리의 모든 것(환자 번호 대조 `patient_check`, 영상 창의 허락, 비교, 반출)이 이 번호로 돎 |
| PatientName (0010,0010) | **우리 차트의 `성^이름`** | 영상 창 · CD에 우리 환자의 이름으로 |
| PatientBirthDate · PatientSex | 우리 차트의 값(차트에 있을 때) | 한 환자의 영상끼리 서로 다른 생일을 갖지 않게 |
| OtherPatientIDs (0010,1000) · OtherPatientNames (0010,1001) | **원래의 번호 · 원래의 이름** | 어디서 온 누구의 영상이었는지를 영상 자체에 남김 |
| IssuerOfPatientID (0010,0021) | 지움 | 「이 번호를 그 병원이 매겼다」는 말이 우리 번호에 붙어 있으면 틀린 말이 됨 |
| StudyInstanceUID (0020,000D) | **새 번호**(우리 규칙 `1.2.826.0.1.3680043.<날짜>.<오더>.<난수>`) | EMR은 오더와 영상을 이 번호 하나로 잇습니다 — 오더마다 우리가 매긴, 겹칠 수 없는 번호여야 「옮기기 · 되찾기 · 복원 뒤 다시 적용」이 지금 코드 그대로 돕니다. 원래 번호는 `pacs_import`에 남깁니다. (원래 번호를 그대로 둘 수도 있습니다 — 한 장씩 고칠 때는 Orthanc가 세 번호를 다 지키는 것도 받아 줌, 확인함 — 17절 ㅈ) |
| AccessionNumber (0008,0050) | **우리 규칙 `YYMMDD-<오더 번호>`** | 「accession으로 되찾기」 · 반출의 README가 이 번호를 씀. 원래 값은 `pacs_import`에 |
| SeriesInstanceUID · SOPInstanceUID | **그대로** | 같은 영상을 다시 가져왔을 때 알아보는 근거(7절) |
| InstitutionName · StudyDate · StudyDescription · SeriesDescription · Modality · 장비 이름 | **그대로** | 원래 어디서 언제 무엇을 찍었는지 |
| 그림(Pixel Data) · 전송 구문(압축) · 장비의 사설 태그 | **그대로** | — |
| OriginalAttributesSequence (0400,0561) | (선택) 바꾸기 전의 값을 표준의 자리에 | 17절 ㅅ |

**확인함**(임시 Orthanc 1.12.11, 공개 견본 다섯 — CT 16비트 · MR · 무손실 JPEG 컬러 · 12프레임 Baseline JPEG · JPEG 2000): `POST /instances/{id}/modify {Replace: {…}, Keep: [SeriesInstanceUID, SOPInstanceUID], Force: true}`가 **2~27ms**에 고친 파일을 돌려줌 — 우리 값이 모두 들어가고, 시리즈 · 영상 번호 · 병원 이름 · 날짜 · 설명 · 장비가 그대로이고, **그림의 바이트가 같고**(프레임의 MD5), **전송 구문이 그대로**(.4.70 → .4.70, .4.50 → .4.50, .4.91 → .4.91 — 다시 압축하지 않음), 사설 태그 수가 그대로(179 → 179, 65 → 65), `OtherPatientIDs` · `OtherPatientNames`에 원래 값. `OriginalAttributesSequence`를 시퀀스로 넣는 것도 받아 줌(200 — 내용까지는 보지 않음).

**바꿀 수 없는 것**: 초음파처럼 **그림 안에 찍혀 있는 글자**(환자 이름 · 병원)는 그림의 일부라 그대로입니다. 틀린 것이 아니라 오히려 「어디서 온 영상인지」가 그림에 보입니다.

## 4. 영상 서버에 어떻게 넣나 — 네 가지 길

걱정하신 것: **환자 번호가 우리 것과 우연히 겹치는 외부 파일이, 바꾸기 전 잠깐이라도 우리 환자의 것으로 보이면 안 된다.**

| 길 | 어떻게 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **가** 프로그램이 파일을 고쳐서 올림 | 접수 PC의 프로그램이 DICOM 파일 안의 태그를 직접 고친 뒤 올림 | 영상 서버에는 처음부터 우리 번호로만 들어감 | **DICOM 파일을 고쳐 쓰는 코드를 우리가 새로 써야 함** — 글자 집합 · 길이 · 시퀀스 · 압축된 그림을 다치지 않고 고쳐 쓰는 일은 틀리기 쉽고, 틀리면 환자의 영상이 망가짐. Orthanc에는 이미 그 일을 하는 검증된 기능이 있음 |
| **나** 통째로 올린 뒤 검사를 고침 | 검사 전체를 원래 번호 그대로 올림 → `POST /studies/{id}/modify` → 확인 → 원본 삭제(「영상 옮기기」와 같은 차례) | 이미 지어 본 차례 | **검사 전체가 몇 분 동안 원래 번호로 우리 서버에 있음**(수백 장을 올리는 동안). 끊기면 통째로 남음. 밤 백업이 그 사이에 돌면 원래 번호의 파일이 백업에 들어감 |
| **다** 한 장씩: 올림 → 고친 것을 받음 → 고친 것을 올림 → 원본을 지움 | 영상 **한 장마다** ① 올림 ② `POST /instances/{id}/modify`(고친 파일을 **돌려줄 뿐 저장하지 않음** — 확인함) ③ 고친 파일을 올림 ④ 원본 삭제 | 원래 번호로 있는 것은 **한 번에 한 장, 수십 분의 일 초**. 검사가 모이지 않으므로 「도착한 검사」로 보일 수 없음. 끊겨도 남는 것은 많아야 한 장 | 영상마다 요청 네 번(한 장에 0.05초쯤 더 — 추측; 500장이면 20~30초) |
| **라** 따로 둔 작은 영상 서버에서 고쳐서 넣음 | 「들여오기 전용」 Orthanc를 하나 더 띄워, 거기에 올리고 거기서 고친 뒤 본 서버에는 고친 것만 넣음 | 본 서버는 원래 번호를 **한 번도** 보지 않음 | 컨테이너가 하나 더(지금의 영상 서버가 167MB를 씀 — 확인함; 비슷할 것으로 추측) · compose · 비밀번호 짝짓기 · 설치 묶음이 늘어남. 현지에 돕는 사람이 없는데 돌볼 것이 하나 더 |

**추천: 다.** 가는 「영상을 다치게 할 수 있는 코드」를 새로 쓰는 일이라 피합니다. 나는 원래 번호의 검사가 오래 머뭅니다. 라는 가장 깨끗하지만 돌볼 것이 늘어납니다 — **다와 EMR 쪽 코드가 같으므로**(「어느 Orthanc에서 고치나」의 주소만 다름), 다로 짓고 나중에 필요하면 라로 옮길 수 있게 짭니다.

**다에서 남는 틈과 막는 법**
- **원래 번호의 한 장이 수십 분의 일 초 동안 본 서버에 있음.** EMR의 어떤 화면도 영상 서버를 「환자 번호로」 뒤지지 않고 **오더에 이어진 검사 번호로만** 엽니다(영상 창의 쿠키도 그 검사들만). 그래서 그 한 장은 누구의 화면에도 나오지 않습니다. Orthanc 관리 화면(관리자만)에는 그 순간 보일 수 있습니다.
- **브리지가 그것을 오더에 붙일 수 있나?** 브리지는 「기다리는 오더」의 검사 번호 · accession과 같고 **들어오기를 멈춘 지 60초가 지난(Stable) 검사**만 붙입니다. 한 장은 바로 지워지므로 Stable이 될 수 없습니다. 그래도 EMR의 `/study-arrived`가 **들여오는 중인 검사 번호의 보고는 거절(409)** 하게 합니다(옮기기 때와 같은 장치).
- **끊기면**: `pacs_import`에 원래 검사 번호가 적혀 있으므로, 뒷정리(8절)가 그 번호로 남은 한 장을 찾아 지웁니다(시작할 때 그 번호가 우리 서버에 없음을 확인하므로, 남아 있다면 이 들여오기의 것).
- **밤 백업**: 그 순간의 한 장이 백업에 잡힐 일은 거의 없지만, 들여오기가 되돌려진 경우의 새 검사와 함께 「없어진 영상」 목록(`GET /superseded-images`)에 올려 백업이 버리게 합니다(13절).

**해 보고 알게 된 것 하나 — 설계를 바꿈**: Orthanc는 영상을 「영상 번호(SOPInstanceUID)」만으로 가리지 않고 **환자 번호 + 검사 + 시리즈 + 영상 번호를 합쳐서** 가립니다. 그래서 ① 고친 파일(영상 번호는 같고 환자 · 검사 번호가 다름)을 **원본이 있는 채로 올려도 따로 저장되고**(확인함 — 그래서 「고친 것을 올린 뒤에 원본을 지운다」는 안전한 차례가 가능) ② 이미 들여온 영상의 **원본 파일을 다시 올리면 「이미 있음」이 아니라 새로 저장됩니다**(확인함). → 같은 검사를 두 번 들여오는 것은 Orthanc가 막아 주지 않으므로 **EMR이 올리기 전에 영상 번호로 물어서** 막아야 합니다(7절 — `POST /tools/find {Level: Instance, Query: {SOPInstanceUID}}`가 그 영상들을 돌려줌, 확인함).

## 5. EMR의 오더 — 누가 만드나

**지금의 사실(확인함 — 코드)**
- 영상과 오더를 잇는 것은 `worklist_log`의 한 줄(검사 번호 · accession · 도착 시각 · 장수 · 환자 대조)입니다. 영상 목록 · 영상 창 · 비교 · 인쇄 · 반출 · 옮기기가 모두 **오더(`order_item`)를 열쇠로** 돕니다. → 들여온 검사도 **오더가 있어야** 화면에 나옵니다.
- 오더는 **진료 기록(`consultation`)이 있어야** 만들어집니다(`order_item.consultation_id` · `visit_id`가 비어 있을 수 없음). 진료 기록은 의사가 그 방문을 열 때 생깁니다. 오더를 만드는 곳은 진료 세션의 `consult.routes.js` 하나입니다.
- 장비 워크리스트로 나가는 것은 `worklist_log`의 상태가 `scheduled`인 줄뿐입니다(브리지의 피드). 오더 코드의 「워크리스트 사용」이 꺼져 있으면 `worklist_log` 줄이 아예 안 생깁니다.

**그래서**
- 오더 코드 하나를 새로 둡니다(마이그레이션): **`IMG-EXT` «Imagerie externe (CD / USB)»** — 종류 `imaging`, Modality `OT`, **워크리스트 사용 안 함**, 값 0 Ar. → 이 오더는 낼 때 `worklist_log` 줄이 생기지 않고 **장비 목록에 절대 나가지 않습니다.**
- 들여오기가 끝나는 순간 EMR이 그 오더에 `worklist_log` 줄을 **처음부터 `completed`로** 만듭니다(우리 규칙의 accession과 새 검사 번호, 도착 시각, 장수, 환자 대조 `match`). `scheduled`였던 적이 없으므로 피드에 나갈 수 없습니다. 오더의 Modality는 디스크의 실제 값(CT · MR · US…)으로 바꿔 적습니다 — 목록의 「종류」와 「같은 종류끼리 비교」가 맞게 돌도록.
- 그 뒤로는 우리 영상과 **구별 없이** 같은 코드가 돕니다: 목록, 영상 창(Stone), 「이전 검사와 비교」(우리 CT와 외부 CT를 나란히), 영상 인쇄, 판독, accession으로 되찾기.

**오더를 누가 내나 — 세 가지 길**

| 길 | 흐름 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **1** 의사가 먼저 낸다 | 의사가 진료 화면에서 «Imagerie externe» 오더를 냄(다른 오더와 같은 한 번의 누름) → 영상 담당이 프로그램에서 그 환자의 「아직 영상이 없는 외부 영상 오더」를 골라 들여옴 | 오더를 만드는 길이 하나(진료)로 남음 · 「이 환자의 차트에 바깥 영상을 넣자」는 것이 의사의 결정으로 기록됨 · 수납이 보통 오더처럼 됨 | 의사가 오더를 내기 전에는 못 들여옴. **디스크에 검사가 셋이면 오더도 셋** 필요 |
| **1+** 의사가 하나 내면 나머지는 EMR이 | 길 1과 같되, 디스크에서 검사를 여러 건 고르면 EMR이 **같은 진료 안에 같은 오더를 모자란 만큼 더** 만듦 | 의사는 한 번만 누름 | 진료 세션이 「오더 하나 더 만들기」를 함수로 내줘야 함(PACS가 진료 세션에 `cancelWorklistForOrder`를 내준 것의 반대 방향) |
| **2** 프로그램이 다 한다 | 의사의 오더 없이, 들여올 때 EMR이 그 환자의 **오늘 진료 기록**에 오더를 만듦 | 접수에서 바로 | 오늘 진료 기록이 아직 없으면(의사가 그 방문을 열기 전) **오더를 붙일 곳이 없음** — 접수에서 미리 올려 두는 것은 어차피 안 됨. 수납 권한의 직원이 오더를 만드는 새 길이 생김 |

**추천: 1+.** 길 2는 「접수에서 바로」처럼 보이지만 진료 기록이 있어야 하는 것은 같아서 얻는 것이 작고, 오더를 만드는 문이 하나 더 생깁니다. 1+에서 진료 세션과 맞출 것은 함수 하나입니다. (그것이 어려우면 길 1로 시작: 「오더 하나에 검사 하나, 더 필요하면 의사가 오더를 더 냄」 — 프로그램이 「오더가 N개 더 필요합니다」라고 알려 줌.)

## 6. 환자 확인

- 프로그램이 디스크에서 읽어 보여 주는 것: 이름 · 번호 · 생일 · 성별 · 병원 · 검사 날짜/이름. EMR에서: 이름 · 차트번호 · 생일 · 성별.
- **규칙(추천)**: 생일이 양쪽에 있고 다름 → 빨강 + 체크 글이 바뀜(그래도 진행은 됨 — 외부 병원이 생일을 틀리게 적는 일이 흔해서). 성별이 다름 → 같음. 이름은 판정하지 않음.
- 확인 창에서 본 값(디스크의 이름 · 번호 · 생일 · 성별, 다름 여부, 체크했음)은 `pacs_import`와 변경 기록에 그대로 남습니다 — 나중에 「누가 무엇을 보고 맞다고 했나」를 알 수 있게.
- **EMR이 다시 확인**: 올라오는 영상 한 장마다 「시작할 때 말한 그 검사 · 그 환자 번호의 것인가」를 봅니다(다른 환자의 파일이 섞여 올라오면 그 들여오기를 멈추고 되돌림). 프로그램을 믿지 않습니다.
- 잘못 들여왔을 때: 16절 ⓔ의 「들여오기 취소」(영상 서버에서 그 검사를 지우고 오더를 비움 — 설정 또는 진료 권한, 사유와 변경 기록). 처음 판에 넣을지는 17절.

## 7. 같은 검사를 두 번 · 우리가 구운 CD

올리기 전에 프로그램이 고른 검사의 **영상 번호 목록**을 EMR에 보내고, EMR이 영상 서버에 묻습니다.

| 상황 | 답 |
|---|---|
| 그 영상들이 이미 **이 환자의 오더**에 있음 | 그 줄은 회색: 「déjà importé le 2026-09-30 (Imagerie externe — CT)」 |
| **다른 환자**의 오더에 있음 | 들여오지 않음: 「ces images sont déjà dans le dossier d'un autre patient — voir l'administrateur」(누구인지는 보여 주지 않음). 변경 기록에 한 줄 |
| 디스크의 검사 번호가 **우리 오더의 번호** = 우리가 구운 CD | 「cet examen a été réalisé ici: il est déjà dans le dossier」 |
| 일부만 있음(전에 끊겼다가 되돌려지지 않은 경우 등) | 처음 판에서는 받지 않고 이유를 말함(「이미 일부가 있음」) — 8절의 뒷정리가 돌고 나면 다시 됨 |
| 하나도 없음 | 들여옴 |

## 8. 끊겼을 때 — 반쯤 올라간 검사를 남기지 않기

표 `pacs_import`(새 마이그레이션): 상태(`started` → `done` / `rolled-back` / `cleanup-pending`), 환자, 오더, 새 검사 번호 · accession, 원래 값들(환자 번호 · 이름 · 생일 · 성별 · 병원 · 검사 날짜/이름 · 검사 번호 · accession), 말한 장수 · 받은 장수 · 바이트, 확인 창의 내용, 누가, 시각, 오류.

차례:
1. **시작**(`begin`): 검사 · 공간 · 중복을 다시 확인하고 한 줄(`started`). 새 검사 번호와 accession이 이때 정해짐.
2. **한 장씩**(4절 다). 받은 장수를 적어 감.
3. **끝**(`finish`): 영상 서버의 새 검사가 「말한 장수 그대로, 우리 환자 번호 · 우리 accession, 영상 번호가 보낸 것과 같음」인지 확인 → **한 트랜잭션**으로 `worklist_log` 줄 · 오더의 Modality · `pacs_import` `done` · 변경 기록. **변경 기록을 못 쓰면 끝내지 않음.**

- 3 **전에는 EMR의 어떤 화면에도 아무것도 안 보입니다**(오더에 영상이 붙는 것은 3의 한순간).
- 프로그램이 죽거나, 사람이 취소하거나, 디스크가 긁혀 못 읽거나, 네트워크가 끊기면: **새 검사를 지웁니다**(그것이 우리 번호 · 이 들여오기의 것인지 확인한 뒤에만) + 원래 번호로 남은 한 장이 있으면 지움 → `rolled-back`. 지울 수 없으면(영상 서버가 꺼짐) `cleanup-pending`으로 두고 **서버 시작 20초 뒤와 5분마다** 다시 시도(옮기기의 `resumePending`과 같은 틀). `started`인 채로 10분 동안 소식이 없는 줄도 되돌립니다.
- 되돌려진 뒤에는 처음부터 다시 들여오면 됩니다(디스크가 원본).

## 9. 압축 — 들여올 때 풀지 않음

- **그대로 저장합니다.** 보관하는 것은 원래 병원이 준 바이트 그대로가 옳고, 푸는 것은 필요할 때 할 수 있습니다.
- 화면의 뷰어(Stone)는 영상 서버가 풀어서 보내 주므로 JPEG 2000 · JPEG-LS · RLE도 열립니다. CD 반출은 `VOIR.EXE`가 못 여는 압축이 섞이면 그 사본을 풀어서 내보내게 이미 지었습니다([cd-mini-viewer-design.md](cd-mini-viewer-design.md) 15절).
- **영상 서버도 그리지 못하는 형식**(예: MPEG 동영상)이 있을 수 있습니다. 들여오기가 끝날 때 EMR이 시리즈마다 첫 장을 「그려 보라」고 해서, 안 되는 시리즈는 목록에 「format non affichable ici」로 표시합니다 — 저장은 됩니다(다른 병원의 프로그램으로는 열릴 수 있으므로). **추측**: 이런 것은 드묾.

## 10. 크기 · 저장 공간 · 걸리는 시간

- CT · MRI는 검사 하나가 수백 MB, 심초음파 동영상은 수 GB일 수 있습니다. **목록에 검사마다 장수와 크기**를 보여 주고 고르게 합니다(프로그램이 디스크의 파일 크기를 더함).
- **한도(추천)**: 검사 하나 **2GB**, 한 번에 고른 것의 합 **4GB** — 넘으면 고를 수 없고 이유를 말함(17절 바). 실장님 말씀대로 큰 심초음파 동영상은 들여오지 않는 쪽.
- **서버의 자리**: 영상 서버의 REST는 디스크의 남은 자리를 알려 주지 않습니다(확인함 — `/statistics`에는 쓴 양만). → **브리지가 15초마다 하는 보고에 「저장소가 있는 디스크의 남은 자리」를 더합니다**(브리지는 영상 저장소와 같은 디스크의 폴더를 이미 쓰고 있음 — compose를 고치지 않아도 됨, 지을 때 Docker Desktop에서 값이 맞게 나오는지 확인). EMR은 「남은 자리 < 들여올 크기 × 2 + 5GB」면 받지 않습니다. 밤 백업 디스크의 남은 자리(이미 보고됨)가 모자라면 경고.
- **시간(추측)**: CD는 초당 약 1.7MB로 읽힘(확인함 — 진짜 CD) → 200MB에 2분, 600MB에 6분. USB는 훨씬 빠름. EMR을 거쳐 영상 서버로 가는 길은 초당 18MB쯤(영상 중계를 지을 때 잰 값)이라 CD에서는 읽기가 대부분. 진행 표시와 「취소」.
- **큰 파일 올리기 — 지금은 막혀 있음(확인함)**: EMR의 nginx는 요청 몸통을 **1MB까지만** 받습니다(설정에 한도가 없어 기본값) — 격리 스택에서 2MB를 보내니 413. 영상 한 장이 1MB를 넘는 일은 흔합니다. → `frontend/nginx.conf`에 **들여오기 길에만** 한도를 풀고 받아 두지 않고 흘려보내는 블록이 필요합니다(공용 파일 — 총괄, 17절 ㄴ).

## 11. 「외부」 표시 · 판독 · 인쇄 · 반출

- **목록**(`RadiologyReadings`): 줄에 「Externe」 이름표, 상세에 「Images d'un autre établissement : HJRA — examen du 2026-08-14 (CT ABDOMEN AVEC CONTRASTE) — importées le 2026-10-02 par …」. 영상 창 위에도 한 줄. `GET /readings/patient` · `viewer-url`의 응답에 `external: {institution, study_date, description, imported_at, imported_by}`.
- **날짜**: 목록의 날짜는 지금처럼 방문 날짜(들여온 날)이고, **원래 검사 날짜**는 상세와 영상 창에. 「이전 검사와 비교」의 차례는 방문 날짜 기준이라 외부 영상이 실제보다 「최근」으로 놓일 수 있음 — 비교 목록에는 원래 날짜를 함께 보여 줍니다.
- **판독(추천: 쓸 수 있게)**: 우리 의사가 바깥 영상을 보고 소견을 남기는 것은 진료의 일부입니다. 다만 **판독 보고서를 인쇄하면 「Examen réalisé à l'extérieur : HJRA, 2026-08-14」** 가 찍혀 우리가 찍은 검사로 읽히지 않게 합니다.
- **영상 인쇄**: 되고, 꼬리말에 같은 한 줄.
- **CD 반출(추천: 넣을 수 있게)**: 환자가 자기 영상을 한 장에 모아 가는 것은 자연스럽습니다. `README.TXT`의 검사 줄에 「(images d'un autre établissement : HJRA)」. 영상 안의 병원 이름은 원래 병원 그대로입니다.
- **영상 옮기기(`pacs.move`)**: 외부 영상 오더는 옮기기 · 맞바꾸기의 대상에서 뺍니다(우리 장비의 오더와 바꿀 이유가 없음 — 미리 막는 이유 `EXTERNAL`).

## 12. 수납

- 오더 코드 `IMG-EXT`의 값은 **0 Ar**로 넣습니다 → 수납에는 0원 줄로 지나갑니다.
- **「등록비」를 받으려면** 설정 → 오더 코드에서 그 코드의 값을 바꾸면 됩니다(코드를 고칠 일 없음). 받을지, 얼마인지는 실장님 결정(17절 마).

## 13. 백업 · 되찾기와의 관계

- **영상 백업**(밤): 들여온 영상은 새 영상이므로 다음 백업에 그대로 들어갑니다. 큰 CT를 여러 건 들여오면 백업 디스크가 그만큼 찹니다(10절의 경고).
- **되돌린 들여오기의 영상이 백업에 들어간 경우**: `GET /superseded-images`(옮기기 때 만든 「영상 서버에서 없어진 영상」 목록)에 되돌려진 들여오기의 새 검사 번호를 더합니다 → 백업이 그것을 버리고, 복원 때 되살아나지 않습니다.
- **복원 뒤**: 들여온 검사는 우리 번호로 백업돼 있으므로 다른 영상처럼 돌아옵니다. `pacs_import` 표는 EMR 백업에 들어 있습니다.
- **accession으로 되찾기**: 들여온 검사도 우리 accession을 가지므로 같은 장치가 그대로 돕니다.

## 14. 권한 · 기록 · 보안

- **누가**(추천): 반출과 같은 사람 — `consultation` 또는 `payment` 권한(17절 사). 본인 계정으로 로그인(프로그램이 이미 그렇게 함).
- **변경 기록**: `pacs.images.import` — 누가 · 환자 · 요약(「1 exam, 412 image(s), 218 MB brought in: CT ABDOMEN AVEC CONTRASTE (HJRA, 2026-08-14) -> Imagerie externe (261002-917)」) · 원래 환자 번호와 이름 · 생일/성별이 달랐는지. 되돌림 · 거절(다른 환자의 영상) · 취소도 한 줄씩.
- **디스크의 다른 것**: 프로그램은 `DICM` 표시가 있는 파일만 엽니다. 디스크의 실행 파일 · DLL · `AUTORUN.INF` · 다른 회사 뷰어는 **실행하지도 복사하지도 읽지도 않습니다.**
- **망가지거나 꾸며진 파일**: 영상 서버가 DICOM이 아닌 것을 받지 않습니다(확인함 — 글자 파일 400, `DICOMDIR` 자체는 404로 거절). EMR은 올라온 한 장이 「말한 검사의 것」이 아니면 버립니다. 프로그램의 DICOM 읽기는 `VOIR.EXE`의 것(깨진 파일 75개 · 망가뜨린 600개에 죽지 않음을 확인한 코드)을 같이 씁니다.
- **영상 서버의 비밀번호**는 지금처럼 EMR 서버에만 있습니다.

## 18. 해 본 것 · 확인 못 한 것

**해 본 것**(임시 Orthanc 127.0.0.1:9196 · 격리 EMR 9188, 공개 견본과 가짜 환자 — 끝나고 볼륨째 지움)
- 한 장씩 고치기(`/instances/{id}/modify`): 3절의 결과. 고친 파일은 **돌려받을 뿐 저장되지 않고**, 저장된 원본은 그대로.
- 고친 파일을 원본이 있는 채로 올림 → 따로 저장됨. 서로 다른 검사의 영상 넷을 같은 새 검사 번호로 고쳐 올림 → **한 검사**(시리즈 넷, 환자 26-00001, accession 우리 것)로 모임.
- 원본을 다시 올림 → 새로 저장됨(「이미 있음」이 아님). 영상 번호로 물으면 두 영상이 다 나옴 → 중복은 EMR이 물어서 막아야 함.
- `DICOMDIR`을 영상인 것처럼 올림 → 404 거절. 글자 파일 → 400 거절.
- EMR의 nginx: 0.9MB 몸통은 통과(401 — 로그인 없음), **2MB는 413**.
- 실행 중 영상 서버의 메모리 167MB(읽기만).
- EMR의 코드: 오더는 진료 기록이 있어야 함 · 워크리스트를 끈 오더 코드는 `worklist_log` 줄을 안 만듦 · 피드는 `scheduled`만 · 권한 이름(`consultation` · `payment` · `registration` …).

**확인 못 한 것**
- 진짜 다른 병원의 디스크(여러 회사의 PACS가 구운 것) — 실장님의 반출 CD 한 장(GE 초음파, 다른 회사 PACS가 구움)의 `DICOMDIR`은 뷰어가 읽었습니다([cd-mini-viewer-design.md](cd-mini-viewer-design.md) 14절). 파일 이름 규칙 · 글자 집합 · 여러 환자가 든 디스크는 지으면서.
- 수백 장 · 수백 MB를 한 장씩 넣을 때의 실제 시간, 영상 서버가 그 사이 다른 일(장비의 전송 · 영상 창)을 버티는지.
- 영상 번호 **여러 개를 한 번에** 묻는 것(`SOPInstanceUID`에 목록) — 검사 번호로는 되는 것을 쓰고 있음, 영상 번호로는 지을 때 확인.
- Docker Desktop에서 브리지가 읽는 「남은 자리」가 호스트 디스크의 값인지.
- `IssuerOfPatientID`를 지우는 것 · `OriginalAttributesSequence`의 내용.
- 한국어 · 프랑스어 악센트가 든 원래 이름이 `OtherPatientNames`에 깨지지 않고 들어가는지(견본은 영어 이름).
