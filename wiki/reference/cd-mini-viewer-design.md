## 1. 한눈에

| | |

| 무엇 | 디스크(또는 폴더)의 영상을 **보기만** 하는 Windows 프로그램 하나 — `VOIR.EXE`. 받는 사람이 더블클릭하면 그 디스크의 환자 · 검사 · 영상이 열림 |
| 크기 | **수백 KB**(목표 1MB 안쪽 — 추측. 시험 삼아 만든 빈 창 프로그램은 4~6KB였음, 확인함). Weasis는 139MB |
| 받는 PC에 필요한 것 | 없음 — Windows 10(1903부터) · 11에 들어 있는 .NET Framework 4.8로 돎(설계안 11절과 같은 길, 확인함). 64비트 · 32비트 모두 |

## 3. 디스크의 모양

```
DICOMDIR · IMAGES\ · README.TXT      ← 지금과 같음
VOIR.EXE                             ← 작은 뷰어. 늘 넣음(수백 KB)
```

- **늘 넣습니다**: 크기가 무시할 만하고 받는 PC에 아무것도 남기지 않으므로 체크 없이 모든 디스크에. `README.TXT`: 「Sans logiciel d'imagerie : double-cliquez sur VOIR.EXE」.
- **만드는 법**: 뷰어의 소스(C# 파일)를 PACS 폴더에 두고, **반출 프로그램이 그 자리에서 실행 파일로 만들어** 디스크에 넣습니다. 확인함(이 PC, scratch): PowerShell의 `Add-Type -OutputAssembly VOIR.EXE -OutputType WindowsApplication`이 0.14초 만에 실행 파일을 만들고, 그것이 실행됨. → 저장소에 실행 파일을 넣지 않아도 되고, 따로 빌드 도구도 필요 없습니다. (반출 프로그램을 나중에 `.exe`로 만들 때는 같은 소스를 `csc`로 함께 빌드 — 앞 설계안 11절.)
- Weasis 때의 「뷰어 넣기」 얼개(`cd-viewer` 폴더 → `VIEWER\`, 체크 칸)는 ①을 지으면서 **없앴습니다** — 작은 뷰어는 파일 하나라 디스크 맨 위에 `VOIR.EXE`로 늘 들어갑니다.

## 4. 가장 큰 불확실성 — 영상의 압축(전송 구문)

DICOM 영상은 장비 설정에 따라 여러 방식으로 압축되어 옵니다. 뷰어가 모든 방식을 직접 풀려면 큰 라이브러리가 필요합니다. 그래서 **「뷰어가 직접 여는 것」을 Windows가 풀 수 있는 범위로 잡고, 나머지는 디스크를 만들 때 영상 서버가 풀어서 내보내게** 합니다.

### 4-1. 실제 장비는 무엇을 보내나

- **확인함**(Mindray DP-10/20/30 초음파의 DICOM 적합성 선언서 원문): 보내는 종류는 「US Image Storage」 · 「US Multiframe Image Storage」(동영상) · 「Secondary Capture」. 내놓는 전송 구문은 **Implicit/Explicit VR Little Endian(압축 없음) · Explicit VR Big Endian · JPEG Baseline(.4.50, 손실) · JPEG Lossless(.4.70) · RLE Lossless(.5) · JPEG 2000 무손실(.4.90) · JPEG 2000(.4.91)**. 색 표현은 "RGB, for color images; MONOCHROME2, if the image is grayscale; YBR_FULL_422, if the image is sent …"(JPEG로 보낼 때).
- 검색 결과로 읽음(원문 PDF를 직접 열지는 않음): GE LOGIQ · Voluson 계열도 압축 없음 · RLE · JPEG Baseline · JPEG Lossless(· 기종에 따라 JPEG 2000)를 내놓음.
- **확인함**(DICOM 표준 PS3.3 C.8.5.6, 초음파 영상): 색 표현은 "MONOCHROME2, PALETTE COLOR, RGB, YBR_FULL, YBR_FULL_422, YBR_RCT, YBR_ICT, YBR_PARTIAL_420" 가운데 하나이고, "YBR_FULL_422 for JPEG lossy compressed Transfer Syntaxes", "YBR_FULL or RGB for RLE Transfer Syntaxes".
- 그러니까 **장비 한 대가 여러 방식을 다 내놓고, 그중 무엇으로 오는지는 장비의 설정과 영상 서버가 받아 주는 목록으로 정해집니다.** 현지 장비가 실제로 무엇을 보내는지는 **추측하지 않습니다.**
- **실장님의 진짜 초음파 — 확인함(2026-10-02)**. 실장님 병원의 PACS가 구운 반출 CD의 영상 55개(총괄이 scratch에 복사해 둔 것을 읽기만 함. 이름 · 생년월일은 읽지도 적지도 않음):

| | |
|---|---|
| 장비 | GE Healthcare **LOGIQ P10**(소프트웨어 R4.5.4) |
| 영상 종류 | Ultrasound Image Storage(`1.2.840.10008.5.1.4.1.1.6.1`), 55개 모두 **한 프레임** |
| 전송 구문 | **JPEG Lossless, Non-Hierarchical, First-Order Prediction (Process 14 SV1) — `1.2.840.10008.1.2.4.70`** |
| 화면 | 1552×873, **RGB**(Samples 3 · Planar 0), 8비트(Allocated 8 · Stored 8 · HighBit 7), 부호 없음 |
| 그 밖 | 밝기 창 없음 · 문자 집합 태그 없음 · Lossy 표시 「00」 · SequenceOfUltrasoundRegions 1 · 가로세로 비 없음 |
| 파일 | 1.28~1.46MB(압축 안 하면 4.06MB — **원래의 32~37%**), 합쳐 74.9MB |
| JPEG 조각 | 조각 2개(첫 조각 = 빈 오프셋 표) · 머리에 `APP0(JFIF)` · `COM` · `DHT` · `SOF3`(8비트, 성분 3개 id 1·2·3, 1×1) · `SOS`(예측 방식 1, 점 변환 0) |
| 그 CD의 `DICOMDIR` | PATIENT 1 · STUDY 1 · SERIES 1 · IMAGE 55, 파일 이름이 `DICOM\번호\번호\번호.dcm` 꼴(확장자 있음), 영상 번호 0~54 |

  - 그림의 99% 이상이 흑백(R=G=B)이고 색이 든 픽셀은 0.8~0.9%(화면의 글자 · 표시)입니다 — 그래도 RGB로 옵니다.
  - 이 파일들은 실장님의 실제 개인정보라서 **저장소 · 위키 · 견본 그림에 넣지 않았고, scratch에서만 읽었고, 실행 중인 영상 서버에 올리지 않았습니다**(임시 서버에 올려 시험하고 그 볼륨째 지움).
  - 이 CD에는 동영상이 없었습니다. 현지에는 심초음파가 없어 **동영상 재생은 만들지 않기로** 했습니다(맨 위).

### 4-2. Windows에 들어 있는 기능으로 풀리는 것 — 해 봄

격리 스택의 시험 영상(컬러 초음파 한 장 800×600 · 12프레임 동영상 640×480 · 12비트 흉부 필름 2500×3000)을 영상 서버로 여러 방식으로 압축해, 그 안의 프레임을 꺼내 Windows의 그림 기능(GDI+와 WIC — 둘 다 .NET Framework에서 바로 씀)으로 열어 봤습니다(이 PC, Windows 11).

| 프레임의 형식 | GDI+ | WIC | 비고 |
|---|---|---|---|
| JPEG Baseline, 8비트 흑백 | ✔ | ✔ | |
| JPEG Baseline, 8비트 컬러(YBR_FULL_422) | ✔ | ✔ | 색이 원본과 맞음(손실 압축만큼의 차이: R43→49 정도) |
| JPEG Extended(.4.51)인데 8비트 | ✔ | ✔ | |
| JPEG Lossless(.4.57 · .4.70), **8비트** 흑백 · 컬러 | ✔ | ✔ | 컬러의 픽셀 값이 원본과 **똑같음**(R43 G43 B153) |
| JPEG, **12비트 · 16비트**(손실 · 무손실) | ✘ | ✘ | "Unsupported JPEG data precision 12 / 16" |
| JPEG-LS | ✘ | ✘ | |
| JPEG 2000 | ✘ | ✘ | |

- **빠르기**(확인함): JPEG 프레임 한 장을 푸는 데 640×480 흑백 5.8ms, 800×600 컬러 3.5ms — 초당 30장 재생에 넉넉함.
- **진짜 파일에서는 달랐습니다(2026-10-02, 확인함)**: 위 표는 영상 서버가 압축한 가짜 영상의 결과입니다. 실장님의 GE 영상 55개를 같은 방법으로 열어 보니 — **GDI+는 55개 모두 실패**(「Unsupported color conversion request」: 머리에 JFIF 표시가 있는 3성분 무손실 JPEG를 GDI+가 「밝기 · 색차」로 여기고 바꾸려다 그만둠), **WIC는 55개 모두 열림**(영상 서버의 그림과 한 픽셀도 다르지 않음, 한 장에 평균 16ms). 같은 「무손실 JPEG 8비트 컬러」라도 만든 쪽에 따라 Windows의 두 기능이 갈립니다.
- **그래서 무손실 JPEG는 Windows에 맡기지 않고 뷰어가 직접 풉니다**(14절). 병원의 장비가 바로 이 형식인데, Windows의 어느 판이 이것을 여는지는 문서에 없고 우리가 시험할 수 있는 PC는 한 대뿐이기 때문입니다. 직접 풀면 받는 PC의 Windows와 상관없이 같은 결과가 나오고, 12 · 16비트 무손실도 함께 됩니다. 손실 JPEG(8비트)는 Windows의 기능(GDI+ — Windows XP부터 있는 기본 JPEG)에 맡깁니다.
- RLE는 Windows에 없지만 **풀기가 아주 단순한 방식**이라(수십 줄) 뷰어가 직접 풉니다(추측이 아니라 형식이 그렇음 — DICOM PS3.5 부록 G의 PackBits).

### 4-3. 영상 서버가 「풀어서」 내보내 주는가 — 해 봄

지금 쓰는 이미지(Orthanc **1.12.11**, GDCM 플러그인 포함 — 확인함)로, 임시 서버(127.0.0.1:9196)에서:

- **묶음을 만들 때 전송 구문을 바꿔 달라고 할 수 있음(확인함)**: `POST /tools/create-media-extended {Resources, Synchronous, "Transcode": "1.2.840.10008.1.2.1"}`. JPEG Baseline · Extended · Lossless · JPEG-LS · JPEG 2000이 섞인 검사(20건)를 넣었더니 **20건 모두 「Explicit VR Little Endian(압축 없음)」으로** 나왔습니다. `DICOMDIR`도 함께.
- RLE · JPEG 2000(YBR_RCT) · JPEG(YBR_FULL) · Big Endian 견본도 한 건씩 넣어 **모두 압축 없음으로 풀려 나옴**(확인함).
- 반대로 `"Transcode": JPEG Baseline`을 주면 8비트 영상은 모두 JPEG Baseline(손실)으로 **다시 압축**되고, 12비트 필름은 그대로 남습니다 — 원본을 손실 압축으로 바꾸는 일이라 **쓰지 않습니다**.
- 한 묶음에 **하나의 목표만** 줄 수 있습니다(영상마다 다르게는 안 됨).
- 영상 서버 자신은 RLE로 **압축해 주지는** 못합니다("Cannot transcode to transfer syntax: 1.2.840.10008.1.2.5") — 푸는 것은 됨.
- 크기(확인함): 위 20건이 압축된 채로 22MB, 풀면 **126MB**.

**지으면서가 아니라 조사하다 찾은 결함 하나 — 고쳤습니다**: 묶음을 만들 때 **같은 검사를 두 번** 적으면 영상 서버가 **끝내 응답하지 않습니다**(Orthanc 1.12.11, 15초 · 300초 기다려 봄). EMR의 `GET /export/bundle`은 두 오더가 같은 검사를 가리킬 때(accession으로 같은 영상에 이어진 경우) 그 검사를 두 번 적을 수 있었습니다 → 한 번만 적게 고침(`pacs.export.js`). 격리에서 확인: 두 오더 · 한 검사 → 0.7초 만에 영상 3장, 기록에도 3장.

### 4-4. 작은 시험 — 정말 읽고 그릴 수 있나 (해 봄)

설계의 근거로 삼으려고 **코드 조각**을 하나 써서 돌려 봤습니다(제품이 아님 — scratch에만 있음). C# **179줄**, Windows에 든 컴파일러로 0.13초에 컴파일, 따로 실행 파일로 만들면 **11KB**.

- **`DICOMDIR` 읽기**: 견본 디스크 폴더(가짜 환자, 검사 2건)의 목록을 4~8ms에 — 환자 1 · 검사 2 · 시리즈 6 · 영상 23, 영상마다 가리키는 파일.
- **그 디스크의 영상을 모두 열어 그려서, 영상 서버(임시 Orthanc)가 그린 그림과 픽셀을 견줌**:

| 영상 | 그리는 데 | 영상 서버의 그림과 |
|---|---|---|
| 12비트 흉부 필름 2500×3000(영상에 적힌 밝기 창 2048/4096) | 21~23ms | 가장 큰 차이 **1/255**(반올림) |
| 흑백이 뒤집힌 필름(MONOCHROME1) 1250×1500 | 8~9ms | 가장 큰 차이 1/255 — 뒤집힘이 바르게 됨 |
| 컬러 초음파 한 장 800×600(RGB) | 1ms | **똑같음** |
| 12프레임 동영상 640×480(8비트 흑백, 압축 없음) — 첫 프레임 · 끝 프레임 | 1ms 안쪽 | 가장 큰 차이 1/255 |
| 같은 컬러 영상을 JPEG Baseline(YBR_FULL_422)으로 압축한 것 | 프레임마다 6ms | **똑같음**(Windows가 푼 색 = 영상 서버가 푼 색) |
| 같은 동영상을 JPEG Baseline으로 압축한 것(12프레임) | 프레임마다 1.7ms | 가장 큰 차이 1/255 |
| 무손실 JPEG(8비트)로 압축한 것 — 컬러 / 동영상 | 6ms / 2.2ms | 똑같음 / 1/255 |

- 장비 보고서(그림이 없는 자료)는 「그림 없음」으로 알아보고 건너뜀.
- 하나 배운 것: 밝기 창이 적혀 있지 않은 **8비트** 영상은 「있는 그대로」 그려야 영상 서버와 같아집니다(최소~최대로 늘리면 달라짐 — 처음에 그렇게 해서 차이가 67/255까지 났고, 고친 뒤 1/255). 6절의 표에 넣었습니다.
- **이 시험이 말해 주지 않는 것**: 진짜 장비의 영상(이 시험은 가짜 영상), PALETTE COLOR, 압축 없는 YBR, RLE, 16비트 부호 있는 영상, 화면에서의 조작 — ①~④에서 견본으로 하나씩 확인할 것들입니다.

### 4-5. 그래서 규칙

| 영상의 형식 | 디스크에 어떻게 | 뷰어가 어떻게 |
|---|---|---|
| 압축 없음(Implicit / Explicit VR LE) | 그대로 | 직접 읽음 |
| **무손실 JPEG**(.4.57 · .4.70, 8~16비트) — **병원의 GE 초음파가 이것** | **그대로** | **뷰어가 직접 풂**(표준 T.81 부록 H의 규칙 그대로 — 값이 원본과 똑같음) |
| 손실 JPEG **8비트**(Baseline .4.50 · Extended .4.51) | **그대로** | Windows의 기능(GDI+)으로 풂. 색의 뜻(RGB인지 밝기 · 색차인지)은 DICOM 파일에 적힌 대로 알려 줌 |
| RLE(8비트 흑백 · 컬러, 16비트 흑백) | 그대로 | 직접 풂(15절) |
| **그 밖**(12비트 손실 JPEG, JPEG-LS, JPEG 2000, Big Endian, MPEG 등) | 고른 검사에 하나라도 있으면 **그 묶음 전체를 「압축 없음」으로 풀어서**(영상 서버가) | 직접 읽음 |

- **왜 「늘 풀어서」가 아닌가**: 초음파 동영상 때문입니다. 800×600 컬러 100프레임이면 압축 없이 **144MB**, JPEG로는 그 10~20분의 1(추측 — 시험 그림에서는 컬러 한 장이 14분의 1, 흑백 동영상이 5분의 1이었음, 확인함). 다 풀면 CD 한 장에 동영상 네댓 개밖에 못 넣습니다. 장비가 JPEG로 보낸 동영상은 **그대로** 두는 것이 맞습니다.
- **「그 밖」이 섞였을 때의 대가**: 그 묶음은 전체가 풀리므로 같이 고른 JPEG 동영상도 커집니다. 반출 프로그램은 받은 뒤의 **실제 크기**로 디스크에 들어가는지를 다시 봅니다(지금도 굽기 전에 이미지 크기를 재서 넘치면 굽지 않음). 흔한 일은 아닐 것으로 봅니다(추측) — X-ray를 JPEG 2000으로 보내게 설정한 장비가 있을 때.
- **EMR이 하는 일**(지음 — 15절): 묶음을 만들기 전에 고른 검사들의 영상이 어떤 전송 구문으로 저장돼 있는지 영상 서버에 묻고(검사마다 한 번: `POST /tools/find {Level: Instance, ParentStudy, ResponseContent: [Metadata]}`), 「그 밖」이 하나라도 있으면 `Transcode`를 붙입니다. 변경 기록 줄에 「unpacked」와 어떤 전송 구문 때문이었는지를 적습니다. JPEG Extended(.4.51)는 8비트면 뷰어가 열지만 EMR은 12비트와 가를 수 없어 「그 밖」으로 칩니다.
- **기본 뷰어가 못 여는 영상이 그래도 남으면**(예: Windows 10에서 무손실 JPEG가 안 열리는 경우): 그 영상 자리에 「Cette image ne peut pas être affichée ici — ouvrez le disque avec un logiciel d'imagerie」. 다른 영상은 그대로 보임.
- **생각해 볼 다른 길 — 영상 서버가 받는 형식을 좁히기**: Orthanc의 설정으로 「받아 주는 전송 구문」을 좁히면(JPEG 2000 · JPEG-LS · MPEG를 받지 않음) 장비는 다른 방식으로 보내게 되어, 처음부터 「그 밖」이 생기지 않습니다. Orthanc를 고치는 것이 아니라 설정이지만, **장비가 붙는 방식을 바꾸는 일**이라 현지 장비가 정해진 뒤에 따로 결정할 일로 둡니다(12절 다).

## 6. 표시의 정확성 — 지켜야 할 것

보기 전용이라도 **틀리게 보이면 안 되는 것**들입니다. 단계마다 견본 영상으로 영상 서버가 그린 그림(`/rendered`)과 견줘 확인합니다.

| 항목 | 어떻게 |
|---|---|
| 흑백의 방향(MONOCHROME1 / 2) | MONOCHROME1은 뒤집어서 — 안 그러면 X-ray가 음화로 보임 |
| 밝기 창(Window Center / Width) | 영상에 적힌 값으로 시작(여러 개면 첫째). 없으면 **8비트는 있는 그대로**, 그 이상은 픽셀의 최소~최대(4-4절에서 겪음). 사람이 끌어서 바꿈 |
| Rescale(Slope / Intercept) | 창을 적용하기 전에 적용 |
| 비트 수(8 / 10 / 12 / 16), 부호 | `BitsAllocated` · `BitsStored` · `HighBit` · `PixelRepresentation`대로 — 안 쓰는 윗비트를 가림 |
| 컬러 | RGB(점 순서 / 면 순서 `PlanarConfiguration`) · **YBR_FULL / YBR_FULL_422**(압축 없는 것은 식으로 바꿈, JPEG는 Windows가 바꿔 줌) · **PALETTE COLOR**(초음파에 흔함 — 색표를 읽어 적용) |
| 여러 프레임 | `NumberOfFrames`, 프레임 시간(`FrameTime` · `RecommendedDisplayFrameRate` · `CineRate`) |

| 영상 방향 | 저장된 그대로 그림(돌리거나 뒤집지 않음). `PatientOrientation` · `Laterality`가 있으면 글자로 보여 줌 |
| 글자 | 환자 이름 · 설명의 문자 집합(`SpecificCharacterSet` — UTF-8, Latin-1) — 악센트가 깨지지 않게 |

## 14. 지은 것 — 단계 ② JPEG (2026-10-02)

`viewer\`에 `Jpeg.cs`가 더해져 **여덟 파일 1,060줄**, 실행 파일 **49KB**(49,152바이트).

**되는 것(①에 더해)**
- **무손실 JPEG**(전송 구문 .4.57 · .4.70) — **뷰어가 직접 풉니다**. 8~16비트, 흑백 · 컬러, 예측 방식 1~7, 다시 시작 표시(restart). 병원의 GE LOGIQ P10이 보내는 형식.
- **손실 JPEG 8비트**(.4.50, 그리고 8비트인 .4.51) — Windows의 기능(GDI+)으로. 색의 뜻은 DICOM 파일에 적힌 대로 디코더에 알려 줍니다(아래 「지으면서 찾은 것」).
- 색 표현: RGB · YBR_FULL · 압축 없는 YBR_FULL_422 · PALETTE COLOR(파일 안의 색 표로).
- **여러 프레임짜리 파일**: 휠로 한 장씩 넘겨 봅니다(「fichier à plusieurs images : 6 / 12 (molette)」). 끝 프레임 다음에는 다음 영상으로. ◀ ▶ 단추와 ← → 키는 파일 단위. 재생은 없습니다. 프레임을 가를 수 없는 파일(조각 수가 프레임 수와 다르고 오프셋 표도 없음)은 첫 프레임만 보이고 그렇게 말합니다.
- **목록의 글을 영상에서**(총괄의 주문): `DICOMDIR`을 읽은 뒤 시리즈마다 첫 파일의 머리를 읽어 시리즈 설명 · 검사 설명 · 환자 이름을 바로잡습니다 → 처음부터 「Vésicule」(영상 서버의 `DICOMDIR`은 「Vsicule」). **느려짐**: USB의 견본 디스크(시리즈 6개)에서 목록이 2~11ms(전에는 4~10ms) — 차이를 잴 수 없을 만큼. 진짜 CD에서는 시리즈마다 파일 하나를 더 찾아가므로 시리즈당 0.1~0.3초쯤으로 **추측**(진짜 CD를 굽는 단계에서 잼).

**여전히 안 되는 것 — 말로 알려 줌**(「…compression non prise en charge. Ouvrez le disque avec un logiciel d'imagerie.」): 12비트 손실 JPEG · JPEG-LS · JPEG 2000 · RLE → ③에서 RLE는 뷰어가, 나머지는 EMR이 풀어서 내보냄.

**실장님의 진짜 초음파 55개로 확인한 것**(이름 · 영상은 어디에도 남기지 않음)
- 뷰어의 코드로 55개를 모두 그려 **임시 영상 서버가 그린 그림과 모든 픽셀을 견줌: 55개 모두 차이 0**(한 값도 다르지 않음).
- 빠르기: 한 장을 읽고 풀고 그리는 데 **16~44ms, 평균 21~22ms**(1552×873 컬러). 휠로 넘기기에 넉넉합니다.
- 그 CD의 `DICOMDIR`(다른 회사의 PACS가 만든 것, 파일 이름에 확장자가 있는 꼴)을 뷰어가 읽음: 검사 1 · 시리즈 1 · 영상 55, 파일 55개를 모두 찾음(5~10ms).
- **우리 반출의 묶음에 넣었을 때**: 임시 영상 서버에 올려 `create-media-extended`로 묶으니 55개가 **한 바이트도 다르지 않게**(SHA-256 같음) · 전송 구문 그대로(.4.70) 나옴 · 묶음 20.8MB(ZIP) · 1.6초. 그 묶음의 `DICOMDIR`도 뷰어가 읽음. → 병원의 초음파는 **풀지 않고 그대로** 디스크에 들어가고, 뷰어가 그대로 엽니다.

**가짜 · 공개 견본으로 확인한 것**(`viewer_test.ps1` 25가지 통과)
- 가짜 영상(필름 12비트 · 컬러 한 장 · 12프레임)을 영상 서버가 다시 압축한 20개: .4.50 · .4.51(8비트) · .4.57 · .4.70은 보이고 서버의 그림과 **1/255 이내**(12프레임 파일은 끝 프레임으로 견줌), 필름의 12비트 무손실은 51~64ms. JPEG-LS · JPEG 2000 · 12비트 손실은 「지원하지 않는 압축」.
- pydicom 견본의 손실 JPEG 12개(RGB · YBR_FULL · YBR_FULL_422, 색 부표본 여러 가지, dcmtk · gdcm · 다른 도구가 만든 것): 서버의 그림과 **차이 0**.
- 이상하고 깨진 파일 75개: 여전히 하나도 뷰어를 죽이지 못함(보임 20 · 지원 안 하는 압축 19 · 읽을 수 없음 22 · 그림 없음 10 · 지원 안 함 4).
- **긁힌 디스크 흉내**(`voir_fuzz.ps1`): JPEG 파일 네 가지를 150번씩 망가뜨림(아무 바이트나 바꿈 · 중간에서 자름) — 600번 모두 2초 안에 답함, 죽거나 멈춘 적 없음. 무손실 한 장짜리는 150번 가운데 149번을 「읽을 수 없음」으로 알아봄(데이터의 길이가 맞지 않는 것으로 — 망가진 그림을 말없이 보여 주지 않으려고 넣은 검사).
- 진짜 실행 파일: 견본 폴더에서 0.2~0.25초에 창, 닫은 뒤 폴더 변화 없음, 임시 폴더 · 사용자 폴더에 새로 생긴 것 없음, Windows Defender 탐지 0건.

**지으면서 찾은 것**
- **GDI+는 병원의 진짜 초음파를 열지 못합니다**(4-2절) → 무손실 JPEG를 직접 풀게 함.
- **손실 JPEG의 색**: Windows의 디코더는 3성분 JPEG를 스스로 「밝기 · 색차」로 여깁니다. 그런데 DICOM에는 「RGB 그대로」 넣은 손실 JPEG도 있어서(색 표현 = RGB), 그대로 맡기면 색이 완전히 틀립니다(견본 둘에서 차이 137 · 255/255). → DICOM 파일의 색 표현을 보고, JPEG 조각 머리에 디코더가 알아듣는 표시(「Adobe」 조각의 변환 값 0 또는 1)를 끼워 넣어 알려 줍니다. 고친 뒤 12개 모두 차이 0.
- 잘린 파일: 압축 없는 영상이 중간에서 끝나면 전에는 아래쪽이 검게 나왔는데, 이제 「읽을 수 없음」.

**확인 못 한 것**
- 다른 PC(Windows 10 · 32비트 · 프랑스어 Windows), 다른 백신.
- 무손실 JPEG의 예측 방식 2~7(견본이 모두 방식 1 — .4.70은 방식 1만 씀. 표준의 식대로 짰으나 견본 없음) · 12비트를 넘는 무손실 흑백의 진짜 장비 영상.
- PALETTE COLOR(견본이 없음 — 코드만 있음).
- 망가진 **손실** JPEG: Windows의 디코더는 망가진 데까지 그리고 나머지를 회색으로 채워 **말없이** 돌려줍니다 — 뷰어가 알아볼 길이 없습니다(무손실은 알아봄).
- 진짜 CD에서의 속도, 수백 장짜리 시리즈.

## 15. 지은 것 — 단계 ③ RLE · 풀어서 내보내기 (2026-10-02)

**뷰어 — RLE를 직접 풉니다**(`viewer\Rle.cs`, 40줄). DICOM PS3.5 부록 G: 프레임을 「조각(segment)」으로 나눠 — 샘플의 바이트마다 하나, 높은 바이트 먼저 — 각각을 PackBits로 줄인 것. 8비트 흑백 · 8비트 컬러(RGB · YBR_FULL) · 16비트 흑백, 여러 프레임. `viewer\`는 **아홉 파일 1,107줄**, 실행 파일 **49,664바이트**.

**EMR — 뷰어가 못 여는 압축이 섞이면 묶음을 풀어서 내보냅니다**(`GET /api/pacs/export/bundle`)
- 뷰어가 여는 전송 구문: 압축 없음(Implicit · Explicit VR LE) · JPEG Baseline(.4.50) · 무손실 JPEG(.4.57 · .4.70 — **병원의 초음파**) · RLE(.5). 고른 검사의 영상이 모두 이 안이면 **지금처럼 그대로**(영상 서버의 파일과 바이트까지 같음).
- 하나라도 그 밖(JPEG 2000 · JPEG-LS · JPEG Extended · Big Endian · MPEG 등)이면 영상 서버에 `"Transcode": "1.2.840.10008.1.2.1"`(압축 없음)을 붙여 **그 묶음 전체를** 풀어 받습니다 — 한 묶음에는 한 가지 형식만 줄 수 있어서(4-3절). 풀린 것은 디코딩한 그림 그대로라 화질 손실은 없고, 사본이 커집니다.
- 답의 머리말 `X-Export-Unpacked: 1|0`, 변경 기록 줄에 「…, unpacked: …」와 `unpacked_from`(원인이 된 전송 구문). 기록의 크기(MB)는 **저장된 크기**입니다(풀린 크기는 보내기 전에 알 수 없음).
- 영상 서버가 전송 구문을 말해 주지 않으면(옛 판 등) 풀지 않고 그대로 보냅니다 — 반출이 막히지는 않게.
- 반출 프로그램: 끝 안내에 한 줄 — 「(Certaines images étaient dans un format que la visionneuse ne lit pas : toutes les images de cette copie ont été décompressées, sans perte. La copie est plus volumineuse.)」(fr · ko · en). 디스크에 들어가는지는 지금처럼 **받은 뒤의 실제 크기**로 굽기 전에 다시 봅니다.

**크기가 얼마나 느나**
- 병원의 초음파(무손실 JPEG 컬러 1552×873): 한 장 1.3~1.5MB → 풀면 4.06MB, **약 3배**(실장님 영상 55장: 74.9MB → 약 223MB). **다만 이 영상만 고르면 풀리지 않습니다** — 「그 밖」의 검사와 **함께 고를 때만** 같이 풀립니다.
- 격리 시험: 초음파 검사(저장 29.3MB, 영상 23개 가운데 JPEG 2000 · 무손실 JPEG · Baseline JPEG 각 1개) → 풀어서 32.4MB. 필름 검사에 JPEG-LS 한 장을 끼움 → 4개 46.5MB.
- X-ray는 대개 압축 없이 오므로 달라지지 않습니다.

**확인한 것**(격리 스택 EMR 9188 · PACS 9198, 임시 Orthanc 9196, 가짜 환자)
- `export_unpack.py` 10가지: 영상 서버가 영상마다 전송 구문을 답함 / 그대로일 때 23개 `X-Export-Unpacked: 0` / **무손실 JPEG · Baseline JPEG를 끼워도 풀지 않음**(그대로 나감) / JPEG 2000 한 장을 끼우면 그 검사는 23개 모두 압축 없음으로 · 머리말 1 · 기록에 `unpacked_from: 1.2.840.10008.1.2.4.90` / 같은 환자의 다른 검사만 고르면 영향 없음 / 둘을 함께 고르면 26개 모두 풀림 / JPEG-LS · JPEG Extended · Big Endian도 풀림 / 끼운 영상을 지우면 처음과 같음. 앞서의 `export_api.py` 31가지도 그대로 통과.
- `cdx_unpack_test.ps1`(창의 코드로 끝까지): JPEG 2000이 든 검사를 「폴더에 저장」 → 끝 안내에 풀었다는 말(세 언어) → 그 폴더의 영상 23개를 **뷰어의 코드가 모두 엶**(22개 그림 + 장비 보고서 1개), 맨 위 `DICOMDIR · IMAGES · README.TXT · VOIR.EXE`. 작업 폴더에 남은 것 없음. 창 시험 22가지도 그대로 통과.
- RLE(`rle_test.ps1` · `viewer_test.ps1` 25가지): pydicom의 RLE 견본 셋 — 16비트 흑백 / 8비트 컬러 / 8비트 컬러 2프레임 — 이 영상 서버의 그림과 **1/255 이내**(컬러는 0). 망가뜨린 RLE 300개에 죽거나 멈추지 않음.

**알게 된 것**
- 영상 서버(Orthanc 1.12.11 + GDCM)는 **2프레임 RLE 견본의 둘째 프레임을 풀지 못했습니다**(그림 요청 404, 풀어 달라고 하면 한 프레임만 나옴). 뷰어는 두 프레임을 모두 읽습니다(둘째는 첫째의 반전 — 견본이 그렇게 만들어짐 — 인 것으로 확인). → RLE를 「서버가 풀어서」가 아니라 뷰어가 직접 읽게 한 것이 맞았습니다.
- RLE에는 손상을 알아볼 여분이 거의 없습니다: 망가진 RLE 파일 가운데 일부는 **틀린 그림이 말없이** 나옵니다(64×64 견본에서 150번 중 39번). 길이가 맞지 않는 경우만 「읽을 수 없음」. 무손실 JPEG는 거의 다 알아봅니다(14절).

**확인 못 한 것**: 진짜 장비가 보낸 RLE · JPEG 2000(견본은 공개 견본과 영상 서버가 다시 압축한 것) / 16비트 컬러 RLE · 32비트(뷰어는 「지원하지 않음」 — 진료 장비에서는 나오지 않는 형식) / 영상 서버가 못 푸는 형식(MPEG 동영상 등)은 풀리지 않은 채 나가고 뷰어는 「지원하지 않는 압축」이라고 말함(견본 없음) / 아주 큰 검사를 풀 때 걸리는 시간(시험은 수십 MB — 1초 안팎).
